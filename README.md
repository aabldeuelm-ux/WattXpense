# WattXpense

Smart home energy monitoring and electricity expense tracking.

WattXpense ingests readings from meters, MQTT devices and CSV exports, works out what the
electricity costs under a real tariff, and adds a set of AI features that are explicit about
what they know and what they are guessing.

There is no physical meter attached to this project. Every reading in the demo database is
generated by the bundled simulator, and the interface labels it as such on every screen.

## The honesty rules

The guiding constraint for this project is that a number a user might act on must never be
more confident than the data behind it. In practice:

- **Simulated readings are always labelled.** Anything ingested with `source="simulator"` is
  recorded as simulated, and the dashboard shows a persistent banner. The flag is
  `is_simulated` and it is tri-state: `true`, `false`, or unset when a source cannot be
  trusted to declare itself.
- **Forecasts, projected bills, anomaly explanations and savings estimates are labelled
  `is_estimate`.** They are models, not measurements.
- **Partial periods are never compared like-for-like.** A week-to-date figure is suppressed
  rather than compared against a full previous week, and the API says why.
- **Anomaly findings carry their evidence and their possible causes.** A flag that cannot
  explain itself is not reported at all.
- **Model accuracy is measured, not asserted.** Forecasts publish held-out metrics, and fall
  back to a weekday average when there is not enough history, saying so in `method`.
- **A slab bill is priced block by block, never with an average rate.** The example tariff is
  labelled as an example, and a tariff that would leave the highest units unpriced is refused.

## What the AI features actually do

| Feature | Method | What it will not claim |
| --- | --- | --- |
| Forecast | `HistGradientBoostingRegressor` on calendar, lag and rolling-mean features, with a held-out validation split | It will not run below the history minimum; it reports `insufficient_data` and a cold-start note instead |
| Confidence band | Held-out residuals scaled by `BAND_SIGMA` | It will not report a band for a model it could not validate |
| Anomalies | `IsolationForest` on daily energy, peak, night-time energy and high-draw hours, corroborated by a robust z-score | It will not call a quiet weekend unusual, and it will not judge a day whose readings are missing |
| Savings insights | Pattern comparison against your own history | It will not present a hypothesis as a diagnosis; causes are labelled as things to check |
| Written explanation | A **local** model (Ollama by default) rewriting the figures above in plain language | It will not produce a number. Every figure is WattXpense's own, and prose that quotes a figure not in the data is discarded |

Anomaly detection has two deliberate safeguards that are worth knowing about, because both
were added to stop the detector lying:

1. **Each day is compared against previous occurrences of the same weekday** where at least
   three exist. A home that is consistently quieter at the weekend has a pattern, not a fault.
2. **A finding must be corroborated.** The unsupervised detector is trigger-happy by design,
   so a day is only reported when the daily total is a genuine outlier *or* the load profile
   is out of band. When only the profile stands out, the headline says `Unusual load pattern`
   and the reason states that the daily total is normal.

## Requirements

- Python 3.11 or newer
- Node.js 20 or newer, for the dashboard
- Optional, for the written explanations only: [Ollama](https://ollama.com) running locally

## Setup

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e ".[dev]"
```

With MQTT ingestion support:

```bash
.venv/bin/python -m pip install -e ".[mqtt,dev]"
```

## Running it

Start the API. It also serves the built dashboard from the same port, so there is no second
process to manage once the frontend is built.

```bash
.venv/bin/python -m uvicorn backend.app.main:app --port 8011
```

Then load some data. The simulator writes realistic household profiles and deliberately
injects a few faults and a missing day, so the AI features have something real to find.

```bash
.venv/bin/python -m simulator.cli seed --days 35 --url http://127.0.0.1:8011 --reset
```

`seed` prints the anomalies and gaps it planted, which is handy for checking the detector.

For frontend development, run Vite alongside the API:

```bash
cd frontend
npm install
VITE_API_TARGET=http://127.0.0.1:8011 npm run dev
```

To rebuild the production bundle that FastAPI serves:

```bash
cd frontend && npx vite build
```

## Optional: written explanations with a local model

Everything above is calculated by this app. On top of that, WattXpense can hand those
calculations to a **local language model** and ask it to write a short, plain-language summary
and a few practical suggestions. This is the only feature in the project that uses a language
model, and it is entirely optional.

Three rules keep this layer honest:

1. **The model never produces a number.** It receives a small block of aggregated figures that
   the app has already calculated. The API returns that block alongside the generated text, and
   the dashboard renders them in separate, clearly labelled places. If you want to check a
   figure, check the calculated panel, not the prose.
2. **Fabricated figures are rejected.** After generating, every number in the model's text is
   checked against the figures it was given. A kWh total, wattage, percentage or cost that is
   not in the data causes the whole answer to be thrown away and replaced with the calculated
   summary, and the UI says why.
3. **The model never sees device identity.** No device id, name, or location is sent, and the
   prompt forbids naming appliances that the data does not mention. There is no per-appliance
   breakdown to infer from anyway, since the readings are whole-circuit.

### Setting it up

Install [Ollama](https://ollama.com), start it, and pull a model that fits your machine.
A 7B-class instruction model is a reasonable starting point; a small one will be noticeably
slower but works.

```bash
ollama serve                  # start the local server
ollama pull qwen2.5:7b        # fetch a model
ollama list                   # confirm what is installed
```

Then tell WattXpense which model to use. Copy `.env.example` to `.env`, set the model name,
and export it before starting the backend:

```bash
cp .env.example .env
# edit .env, then:
set -a && . ./.env && set +a
```

The relevant variables:

| Variable | Default | Meaning |
| --- | --- | --- |
| `WATTXPENSE_LLM_ENABLED` | `true` | Master switch for the written explanation |
| `WATTXPENSE_LLM_PROVIDER` | `ollama` | Which registered provider to use |
| `WATTXPENSE_LLM_BASE_URL` | `http://127.0.0.1:11434` | Where the local model server listens |
| `WATTXPENSE_LLM_MODEL` | *(empty)* | Model name. **Empty means the feature is off** |
| `WATTXPENSE_LLM_TIMEOUT_SECONDS` | `60` | How long to wait before giving up |
| `WATTXPENSE_LLM_TEMPERATURE` | `0.2` | Lower keeps the model closer to the figures |
| `WATTXPENSE_LLM_KEEP_ALIVE` | `5m` | How long Ollama keeps the model loaded |

There is deliberately no default model name in the code. If `WATTXPENSE_LLM_MODEL` is unset,
generated text stays off and the dashboard says so, rather than silently picking a model you
did not choose.

`.env` is git-ignored. Only `.env.example`, which contains no secrets, is committed. Ollama
needs no API key and no credentials of any kind, so there is nothing secret to store here.

#### "AI unavailable" when Ollama is installed and working

This is the most common confusing result, and it is almost always one of three things. Check
them in this order:

```bash
curl -s http://127.0.0.1:8011/api/ai/status
```

1. **`"not_configured"`** means the model name never reached the running server. `ollama list`
   showing a model is not enough: the *server process* needs the variable in its own
   environment. Starting the backend from a shell where you exported it, or sourcing `.env`
   first, is what fixes it. A server started before you set the variable keeps running
   without it, so it must be restarted, not just reloaded.
2. **`"unreachable"`** means `ollama serve` is not running. Start it in its own terminal; it
   does not start on demand.
3. **`"model_missing"`** means the server is up but the name does not match an installed model.
   Ollama tags matter: `qwen2.5:7b` will not match a model pulled as `qwen2.5-coder:7b`.

To avoid repeating this, export the model once per shell and start the backend from that same
shell:

```bash
export WATTXPENSE_LLM_MODEL=qwen2.5-coder:7b
.venv/bin/python -m uvicorn backend.app.main:app --port 8011
```

A 7B model on CPU typically takes 8–30 seconds to answer. The dashboard shows a pending state
for that window rather than appearing to hang.

### What happens when the model is not available

The written explanation is the only part of the dashboard that depends on a model, and it fails
softly in every case. The API always returns HTTP 200 with `ai_available: false` and a short
reason, and the panel falls back to a summary built from the calculations alone:

| Situation | `status` | What the user sees |
| --- | --- | --- |
| `WATTXPENSE_LLM_MODEL` unset | `not_configured` | "AI unavailable", with the setup steps |
| `WATTXPENSE_LLM_ENABLED=false` | `disabled` | "AI unavailable", with the setup steps |
| Ollama not running | `unreachable` | The reason, and a retry button |
| Model not pulled | `model_missing` | "Pull the model, then try again" |
| Slow model | `timeout` | "The local model took too long to respond" |
| Unusable model output | `malformed` | The model output is discarded |
| Model quoted an invented figure | `ungrounded` | The whole answer is discarded, and the figure is named |

Monitoring, forecasts, anomaly detection and bills never call a model, so they are unaffected in
all of the above. The explanation is also generated on demand from a button rather than on the
dashboard's refresh cycle, so a slow model cannot make the rest of the page feel slow.

### Using a different local model

Providers are registered in one place, `energy_ai/llm/__init__.py`. To add another, implement
`LLMProvider.complete()` in a new module, register it in `PROVIDERS`, and set
`WATTXPENSE_LLM_PROVIDER` to its key. Nothing in `backend/` or the rest of `energy_ai/` needs
to change, and no other module knows which provider is in use.

## The ingestion contract

Every source, whatever it is, has to produce the same shape, and it is validated in one
shared place (`backend/app/ingestion/base.py`) so that a bad MQTT message is treated exactly
the same way as a bad CSV row.

```json
{
  "device_id": "sim-main-01",
  "ts": "2026-09-26T14:00:00Z",
  "voltage": 231.4,
  "current": 3.12,
  "power_w": 721.0,
  "energy_wh": 721.0
}
```

- `ts` must be timezone-aware. A naive timestamp is rejected rather than silently assumed to
  be UTC, and a timestamp in the future is stored but flagged `timestamp_in_future`.
- `energy_wh` is the energy for **one reporting interval**, not a cumulative meter reading.
  A 5-minute sample that measured 60 Wh reports `60`, not a running total.
- `current` and `power_w` can each be derived from the other and the voltage, so a source only
  has to supply what it actually knows.
- Ingesting the same device and timestamp twice updates in place rather than double counting.

returns a JSON 404 rather than the dashboard HTML. That way a mistyped endpoint fails loudly
instead of quietly handing the frontend a page it cannot parse.

### How the projected bill is put together

This is the part that is easiest to get quietly wrong, so it is worth stating plainly.

The projection adds together two disjoint sets of days:

- **Metered days.** Every day in the billing period before today that has at least 90% reading
  coverage. A day with a gap is excluded, not scaled up.
- **Forecast days.** Every day from today through the end of the period, forecast as a whole
  day.

Today is forecast as a whole day rather than added from its part-readings. That means today
can never be counted twice, and today can never be missing. The response reports
`forecast_covers_today` and a `projection_basis` sentence naming the counts, and it states how
much the projection is understated by any day that was skipped.

## Billing

WattXpense is set up for an Indian household: rupees, IST, 230 V at 50 Hz, an evening peak
window, and electricity duty rather than sales tax. Money is grouped the Indian way
(`₹12,34,567.89`), large figures can be read as lakh and crore, and dates are day-first.

### Slab tariffs

Slab (also called "block" or "tiered") tariffs are the default, because that is how most Indian
domestic tariffs are priced: the first block of units is cheap, and each block above it costs
more. Every unit is charged at the rate of the block it falls in, so the bill is worked out
block by block:

```
Energy - First 100 units @ 2.5/INR      100.0 units     250.0
Energy - Units 101-300 @ 4.5/INR        200.0 units     900.0
Energy - Units 301-500 @ 6.5/INR        150.0 units     975.0
Fixed charge                              30.0 days      75.0
Electricity duty (5.0%)                 2125.0 INR      106.25
```

450 units over 30 days comes to ₹2,296.25. A blended rate would not produce that bill, so
WattXpense never uses one to price a slab bill. It does report a blended rate for context
(such as in savings estimates), clearly labelled as an average that changes as consumption
grows.

The top block must be left open ended, meaning no upper bound, so units above the highest
boundary are still billed rather than silently free. WattXpense rejects a tariff that leaves
them unpriced, and also rejects bounds that do not increase and rates that decrease.

Because a slab bill depends on the whole period's consumption, one day's units are charged at
whatever rate the month's total reaches by the end of that day. The dashboard shows today's
contribution at that marginal rate and says so, rather than implying each day is billed on its
own.

### The default tariff is an example, not a real schedule

The tariff created on first run is called "Generic India domestic (example slab tariff)" and is
a worked example of the *shape* of an Indian domestic slab tariff. It is not any particular
DISCOM's published rates, and it is not a claim about what anyone is charged. Enter the
numbers from your own bill in the tariff panel to match a real invoice.

### Other tariff types

Flat and time-of-use tariffs are also supported. The response itemises every line with the
formula that produced it. The fixed charge is billed for every day in the period, including
days still to come, which is how fixed charges actually work. Electricity duty is applied to
the energy charge only and not to the fixed charge, which is the usual Indian treatment; some
DISCOMs include the fixed charge in the duty base, so compare against a real bill and adjust
if yours differs.

## Tests

```bash
.venv/bin/python -m pytest tests/ -q
```

The suite pins the application clock, uses a temporary database, and is deterministic, so it
can run without a server or any seeded data. It covers the billing arithmetic and the day
rollover, ingestion validation and idempotency, aggregation and coverage handling, and the
honesty rules above, including regression tests for the two anomaly safeguards and for the
projected bill not double counting today.

## Limitations

- No physical meter integration is configured out of the box. MQTT polling is implemented but
  needs broker credentials.
- Anomaly causes are hypotheses. Whole-home readings cannot identify which appliance was
  responsible, and the app says so rather than guessing.
- Forecast accuracy degrades with sparse or irregular readings. A household with many gaps
  will see wider bands and more `low` confidence.
- The written explanation is only as good as the model you point it at, and a small local model
  may still produce vague prose. It cannot produce a number the app did not calculate, and
  answers that try are discarded, but a cautious reader should still treat the suggestions as
  prompts rather than findings. It may also name a kind of appliance in passing; the app cannot
  verify that, so treat it as the model's own wording rather than a finding about your home.
- There is no caching of generated explanations. Each request re-runs the model, which keeps the
  wording honest about the current figures but means a slow model is slow every time.
- The default slab tariff is an illustrative example, so a fresh install will not match a real
  bill until you enter your DISCOM's actual rates. The dashboard has been verified through its
  API, its static build and a headless browser pass, not yet through a full manual pass in a
  desktop browser.
- A slab bill assumes consumption accumulates evenly across the month, so a projected slab bill
  can be wrong by more than a flat projection would if the month actually crosses a boundary
  differently. The projection carries a note saying so.
